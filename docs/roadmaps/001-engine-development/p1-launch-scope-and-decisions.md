**Date:** 18 November 2026 · **Decision authority:** Product owner, with engineering evidence · **State of every decision below:** **Open**. This document proposes product choices; no choices were approved by authoring it and no application options have been disabled.

Cross-references: [complete capability inventory](p1-capability-matrix.md), [proposed numerical contract](p1-calculation-contract.md), [qualification baseline](p1-qualification-baseline.md), [RM-001 roadmap](README.md). Inspected Aria Ephemeris `main` `36a9cec`, Aria Galaxy `main` `4ab5f99`.

## Product principle

**Do not launch a planet-labelled commercial chart which quietly substitutes a planetary-system barycentre, silently omits optional/visible points, or displays fabricated ancient/unknown-time precision.** Keep Aria's existing chart and activation semantics, but decide which features the *first Aria-powered offer* genuinely promises. A research-only compatibility demonstration is not a paid release, and a source-code gap is not a deployed limitation until tested in the application.

A sensible **candidate** is a tropical, geocentric core for ordinary date/location charting and bounded activation intervals, inside the engine's 1900–2100 **TT numerical envelope**. That is **not yet a valid civil birth-date promise**: strict engine UTC is unavailable before 1972 and cannot extend beyond the pinned leap-table expiry **2027-06-28** without a controlled policy/update. Commercial date scope must be approved only after P2 evidence.

### Delivery distinction: restricted internal pilot vs first paid launch

An **internal engineering pilot** could compare Sun/Moon/Mercury/Venus, tropical positions, Equal/Whole Sign geometry and bounded TT test instants while marking unsupported bodies unavailable. It is expressly **not** an acceptable silent replacement for Aria Galaxy's current ten-major-planet commercial chart or activation models. This pilot would still require a separately authorised implementation/testing prompt; no pilot was executed by RM-001/001.

For a paid launch, the recommended priority is **definitionally correct planetary targets and dependable dates first**, then user-visible default points and controlled service integration; do not spend P5 budget on a Rust rewrite while core identity and contracts remain unresolved.

## Concrete unsupported-case user/API behaviour

- **Unsupported zodiac/house/body:** capability metadata identifies it; selection is disabled or clearly marked unavailable, a direct API request returns structured `UNSUPPORTED_*`/equivalent error, and imported saved settings cannot silently downgrade. Optional requested objects can be `unavailable` with null value and reason.
- **Missing required body or EOP/dataset:** fail request or mark only affected optional result unavailable; no "last good" snapshot passed off as new data. Retained UI data must remain visibly stale with original timestamp/source.
- **High latitude/polar geometry:** preserve defined ASC/MC when mathematically valid; unavailable house systems remain unavailable. Equal fallback is permitted **only** when expressly requested and recorded.
- **Unresolved historic/approximate civil time:** reject exact chart or hide exact time-sensitive houses/axes; retain event time-quality metadata and uncertainty rather than inventing precision.
- **Date outside qualification or strict leap-table expiry:** show limits before submission and return a stable out-of-range/time-data error if called directly; do not clamp to 1900, 2100 or 2027.
- **Saved and comparison charts:** retain V6 document and old provider identity, validate both snapshots for compatible frame, calculation and dataset, and require deliberate recalculation/migration instead of silently overwriting historical chart results.
- **Chart vs activation:** a `truePositions` range request must never be served from a cache of apparent chart positions; provider/dataset/time/model/target identity belong in cache keys.

## Open evidence and deliberate non-claims

- No actual centre-source solution, civil-time policy, new chart algorithm, app adapter or deployment was delivered in P1.
- Historical DE442s numerical agreement does **not** qualify physical planet centres, additional points, all latitudes, every time input or a deployed UI.
- The `major` range preset's `true_node` fallback is a concrete source-level behaviour requiring an explicit compatibility decision; it must not become an accepted numerical definition by accident.
- Application V6 saved documents and V2 aspect/orb policies are current source facts; older V1/V4 contract docs may remain useful but are not the whole operational product.
